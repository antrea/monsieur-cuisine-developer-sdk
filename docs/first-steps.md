# First Steps: Control a Virtual Appliance

This tutorial uses one local Python process. No robot, manufacturer APK, firmware, Internet service or Android tools are needed for the first experiment.

## 1. Install and open the desktop

Install Python 3.11+ with working Tcl/Tk, open a terminal in the source checkout and run:

```sh
python -m pip install -e .
python -m monsieur_cuisine_sdk
```

Use `python3` on Linux/macOS if needed. If no window opens, follow the platform [setup guide](setup.md) and [troubleshooting](troubleshooting.md).

## 2. Start MCC and watch it accelerate

Select **Monsieur Cuisine Connect (MCC)**. Choose speed **2**, direction **ccw**, and heat **60 °C**. Press **START / Apply**. Requested output changes immediately, while the synthetic observed RPM rises over virtual time.

The dashboard shows motion, temperature, weight, lid, error and simulated firmware. Open **Protocol Monitor** to see the actual 15-byte command and dynamic 27-byte responses. They are real bytes generated by the studied codec, with synthetic state values.

Press **STOP**. The requested target is removed; actual motion decays to zero. Use **Pause** and **Step seconds** to inspect smaller increments. A stopped virtual clock is not a physical motor STOP command.

## 3. Inject an error

Start again at speed 2. Open **Errors**, inject controller error **3**, and inspect the status and HEX output. Error meanings are profile-specific. Press STOP explicitly; do not infer that this host scenario proves a hardware interlock.

Restore error **0** before the next operation. **Scale & Sensors** can also change weight, temperature, lid and NTC state. The [user guide](digital-twin.md) explains each tab.

## 4. Switch to MCS

Select **Monsieur Cuisine Smart (MCS)**. Switching disarms the old model, closes a connected client/listener and creates a fresh isolated session. Repeat speed 2 / ccw / 60 °C.

MCS displays **raw motor level**, not verified physical RPM. Its normal operational wire is 39-byte TX / 48-byte RX, with a variable envelope and independent sequence/checksum. Do not compare a numeric level directly with MCC RPM.

## 5. Perform the same experiment in Python

Create `first_experiment.py` in a working directory of your choice:

```python
from monsieur_cuisine_sdk import DeviceModel, DigitalTwin, replay

for model in (DeviceModel.MCC, DeviceModel.MCS):
    twin = DigitalTwin(model, seed=292)
    twin.start_motor(speed=2, direction="ccw", temperature=60)
    twin.advance(0.5)
    state = twin.get_state()
    print(model.value, state.actual_speed, state.speed_unit)
    assert state.actual_speed > 0
    twin.set_sensors(error_code=3)
    responses = twin.sample()
    print("RX", [frame.hex(" ") for frame in responses])
    twin.stop_motor()
    twin.advance(2)
    assert twin.get_state().actual_speed == 0
    twin.save(f"{model.value}-session.json")
    assert replay(twin.recording).get_state() == twin.get_state()
```

Run `python first_experiment.py`. Virtual time advances without real-time sleeps. The two local JSON files contain synthetic, model-explicit recordings. See [API types and errors](api.md) and [replay policy](recording.md).

## 6. Try the CLI and automated checks

```sh
mc-sdk --model mcc capabilities
mc-sdk --model mcs scenario start_stop
mc-sdk --model mcc conformance
mc-sdk --model mcs conformance
```

Use [Quick Command Reference](quick-commands.md) for common tasks and [testing](tests.md) for the full Tk/loopback suite.

## 7. Add an Android application when ready

Install Android Studio, open `android/`, prepare a standard emulator and build the debug demo. Enable **Android Connection** in the desktop. Match the selected device and connect to `10.0.2.2`: MCC port 8765 or MCS port 8766. START, observe telemetry, STOP and disconnect.

The listener is optional and lives in the same desktop process. No separate bridge or web page is needed. Follow [Android integration](android.md) for lifecycle and [the SDK project](../android/README.md) for dependencies and Kotlin examples.
