# Digital Twin fidelity and assumptions

**MCC Digital Twin / MCC PowerBoard Simulator** is one component of MCC Developer Toolkit: a persistent software state model with the build 292 binary protocol at its boundary. Its primary interface is the native Tkinter/ttk desktop, in one process with no server. “Digital Twin” describes its development role: state can be recorded/replayed and driven through an injected adapter or optional separate loopback/virtual-transport integration. It does not imply perfect reproduction of a physical appliance or recovered MCU code.

## Fidelity matrix

| Layer | Basis | What this implementation can establish |
|---|---|---|
| 15-byte TX / 27-byte RX structure | Static build 292 serializer/decoder evidence | Byte placement, checksum, endian rules, signed weight, supported mappings and unknown-field preservation |
| Incremental input | Original independent parser implementation | Split/concatenated TX handling and diagnostics for malformed input |
| Command targets | Build-specific fields plus chosen model interpretation | Persistent requested speed/direction/temperature state |
| Measured RPM and inertia | Synthetic rates and signed-velocity state | Finite acceleration/deceleration and a chosen zero-crossing reversal rule |
| Thermal response | Piecewise linear synthetic rates | A reproducible temperature trajectory, without a thermal-mass/load model |
| Weight and sensors | Validated injected values | Data-format and application-event testing, not sensor physics |
| Faults and loss | Deterministic configured response faults | Application behavior under delay/drop/corruption/disconnect scenarios |
| Lid/error handling | Injected protocol state; separate program guards | No independent emulation or certification of real hardware/firmware interlocks |
| Recording/replay | Original software event log, RX bytes and checkpoints | Deterministic reproduction of a supported synthetic run |

The [serial specification](../serial-protocol-v292.md) and [evidence ledger](../research-methodology.md) describe the artifact-backed facts. Parameter choices below are **not part of that artifact evidence**.

## Rotational dynamics

The model keeps signed float velocity. Clockwise is positive, counterclockwise negative. RX exposes its rounded absolute magnitude as measured RPM and derives the reported direction from the actual sign while moving. At exactly zero, it reports the requested direction.

Over a virtual interval `dt`, velocity approaches the target by at most `rate × dt`. Defaults are acceleration 4,000 RPM/s, active deceleration 6,000 RPM/s and coasting deceleration 1,000 RPM/s. The target-RPM table is illustrative: `(0, 200, 700, 1200, 2000, 4500, 7500, 10500, 13500, 16500, 19000)` for levels 0–10. These points are chosen examples, not reconstructed controller setpoints.

STOP changes requested speed/temperature to zero, but measured RPM continues until finite model deceleration reaches zero. Its motor-enabled status can therefore be false while measured RPM remains positive. A controller testing WAIT_STOP must inspect both and use a fresh local observation.

For an opposite-direction target, the model first spends the required virtual interval decelerating to zero. Only remaining time in that advance step accelerates in the opposite direction. SLEEP uses the slower coasting coefficient by explicit hypothesis; no corresponding real powerboard braking rule was recovered. No mass, torque, gearing, electrical current, blade load, wear or safe repeated-start frequency is modeled.

## Heating and sensors

The default temperature starts at a chosen 20 °C ambient. When heating is requested it approaches the target with a 1 °C/s increase; cooling approaches target/ambient with a 0.1 °C/s decrease under the model's simple rules. The internal float is rounded/clamped for the unsigned RX field. There is no calorimetry, evaporation, fluid circulation, thermal cutoff or motor-load heat model.

Weight, lid, NTC, scale stability/calibration state, error codes, firmware number and unknown byte 24 are injectable state. They are not generated by physical sensor models. Temperature-above-target and other status flags can be explicitly injected; do not assume every flag is dynamically derived from the thermal value. The default firmware number is synthetic and identifies no device.

Lid-open and error injection do not autonomously stop the low-level virtual controller. The independent intermittent program imposes its own software guards and terminal fault behavior. This distinction lets developers test whether their application responds correctly, without pretending that firmware protection logic has been reconstructed.

## Communication and time

The base model and headless scenarios use explicit virtual milliseconds and no sleeping. A local `serve` preview advances that virtual clock using the host monotonic clock and periodically samples status. It remains a software scheduling service, not real-time embedded execution. Manual-clock mode removes that automatic advance.

Each accepted TX schedules one status snapshot; `.sample()` explicitly schedules another. Configured delay preserves the snapshot's earlier data, so it can arrive after the model state has changed. Drop/corruption frequencies count attempted responses across the model's lifetime. Corruption changes one checksum bit. These are deterministic fault patterns, not measured electrical noise.

Virtual disconnect discards queued RX and partial input, ignores new TX and preserves previous targets. Real TCP disconnect similarly does not imply a model STOP. This intentionally avoids assuming an unproven controller watchdog. A lost STOP must not be reported as successful merely because a socket closed or the host session terminated.

The frame has no discovered request sequence or receive timestamp. Local transport metadata and replay event order do not add such fields to the protocol. An old snapshot received anew cannot be recognized as old solely from its RX bytes.

## Integration and scientific limits

The Python mock adapter and original Kotlin port example support development against an injected interface. Code above a well-defined application seam can retain its domain logic. The proprietary original APK still uses its compiled Binder/serial paths: byte compatibility alone does not redirect that transport. No drop-in binary replacement, APK patch or flashing procedure is supplied. An optional serial-like memory object and fresh POSIX PTY bridge are available; Windows virtual COM emulation is deferred and no driver is installed automatically.

A passing scenario, matching replay or smooth blade animation checks the chosen software model. It does not verify physical braking, firmware watchdogs, safe loads, electrical settings, hardware interlocks or compatibility with another board/launcher version. See the general [safety and limitations](../safety-and-limitations.md).
